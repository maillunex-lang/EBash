# Техническая основа

## Утверждено

- Клиент создаётся на Godot (D-092). Версия — Godot 4.7.2 (D-094). Импорт и smoke-проверка клиента прошли на 4.7.2.
- Клиентский код пишется на GDScript со строгой типизацией (D-093). C# не используется.
- 3D-модели с ортографической камерой создают изометрический вид. Направление камеры фиксировано по [правилам карты](maps.md).
- Графика отрисовывается на телефоне, сервер передаёт данные. Видеотрансляция и HTML/WebGL как основа клиента не выбраны.
- Сервер окончательно проверяет все игровые действия и рассчитывает экономику. Клиент отображает результаты и предварительные оценки; клиентские расчёты не считаются достоверным состоянием мира.
- Начальная организация сервера — одно приложение с разделёнными модулями и отдельным процессом расчёта тиков. Множество независимых сервисов на старте не выбрано.
- **Только игра (D-192).** Развивается единый игровой клиент: меню → республика/компания → карта города → экран предприятия против сервера. Локальный UI-стенд без сервера (бывший «демозавод»), задачи сравнения движков и отдельная линия «демо» не ведутся. Имена вроде `demo-smoke` / `profile-demo` означают изолированный **тестовый игровой мир** для автопроверки, а не продукт-стенд.

Подробности загрузки городов, кеша и целевые показатели: [карты](maps.md). Поведение без связи: [UI](ui.md).

## Эксплуатационные параметры

Стек выбран в D-189, контракт проверок — в D-190. Фактическое размещение и результаты испытаний фиксируются при реализации.

Выбранная организация не означает отсутствие кеша или фоновых компонентов и не требует заранее делить каждую функцию на сервис. Дальнейшее разделение обосновывать измеренной нагрузкой и эксплуатационными требованиями.

## Вход и эксплуатация — утверждено

Вход игрока по email с одноразовым кодом и через внешние аккаунты; провайдеры и связывание способов входа открыты. Можно играть с нескольких устройств; сервер синхронизирует изменения и проверяет конфликты.

Ежедневная резервная копия плюс журнал изменений для восстановления на момент перед сбоем; регулярно проверяется восстановление. Плановые работы проводить между тиками; аварийное восстановление и судьба пропущенных тиков требуют отдельного правила.

Для Unity-прототипа выбиралась Unity Personal (D-091); после выбора Godot Unity-прототип не развивается.


## Согласованные правила

- D-178. После закрытия зависимостей DES-008 сначала проектируется полный серверный цикл до первой продажи со сверкой склада, денег и отчёта. Затем цикл подключается к Godot и проверяется на Android.

## Серверный стек и границы первого среза — D-189

Go для HTTP API и процесса расчёта тиков, PostgreSQL для игрового состояния, журнала команд и транзакций. Оба процесса используют общие модули экономики. Клиент Godot получает версионированный JSON через HTTPS. На первом срезе обновления клиент запрашивает сам. Это позволяет проверить правила экономики на одном источнике состояния и использовать штатные транзакции и ограничения базы.

Предварительный контракт P2. Команда имеет стабильный ID в рамках аккаунта. Повтор с тем же содержимым возвращает сохранённый результат, повтор ID с другим содержимым отклоняется. Тик идентифицируется миром и номером. Расчёт одного мира сериализуется, а применение результатов и запись статуса тика происходят в одной транзакции. Покупка, доставка, выпуск и продажа оставляют отдельные записи склада и денег. Прерванный расчёт повторяется из сохранённых входов, а подтверждённый не применяет проводки повторно.

Приёмка первого контура проверяет отказ до фиксации транзакции, потерю ответа после фиксации, повтор одной команды, повтор тика и восстановление из копии с журналом. Для повторов сверяются итоговые остатки и число проводок. Проверочные данные берутся из [хлебного сценария](../catalogs/wheat-bread.md). Игровой профиль допускается отдельно по D-139.

## Контракт технического среза — D-190

Все изменяющие команды проходят серверную проверку прав и состояния мира. Аутентификация возвращает аккаунт, по которому сервер находит доступную компанию. `company_id` из запроса не определяет права. Публичные рыночные поля формируются отдельным представлением без внутренних затрат. Суммы передаются целыми копейками и количества целыми базовыми единицами. Идентификаторы, счётчики и значения PostgreSQL BIGINT передаются строками в JSON, чтобы клиент не терял точность при разборе.

| Запрос | Вход | Выход |
| --- | --- | --- |
| POST /v1/worlds/{world_id}/commands | `command_id`, `type`, `payload` | 202, ID, статус и целевой тик. Повтор принятой команды с идентичным нормализованным содержимым возвращает сохранённое подтверждение. Другая команда с тем же ID получает 409. |
| GET /v1/worlds/{world_id}/commands/{command_id} | ID собственной команды | Статус `accepted`, `applied` или `rejected`, тик результата и код отказа, если применимо. Чужой ID недоступен. |
| GET /v1/worlds/{world_id}/company | Авторизация | Согласованный снимок денег, остатков, результатов последнего тика и номер `last_committed_tick`. |
| GET /v1/worlds/{world_id}/status | Авторизация | `running` или `recovering`, завершённый и ожидаемый тики. |

Команды первого контура: заказ сырья с ID предложения, количеством и пределом цены, настройка известного профиля линии с ID предприятия и ячейки, выставление готового выпуска с ID партии, количеством и ценой. Фактическую доставку и исполнение рынка подтверждает сервер. Приём команды и её исполнение различаются. Повтор запроса статуса позволяет увидеть результат даже после потери ответа. Операции записи во время восстановления отклоняются с `WORLD_RECOVERING`, кроме чтения подтверждения по уже принятому ID с тем же содержимым.

Хранение PostgreSQL. Отдельно хранятся журнал принятых команд, тики, партии и движения запасов, денежные проводки и версии профилей. Уникальны ID команды в рамках аккаунта и мира, номер тика в мире и ссылка проводки на событие с порядковым номером. На транзакции приёма и фиксации тика используется один барьер мира: строка мира блокируется, граничный тик и режим проверяются под блокировкой. Операция зачисления денег и движения товара фиксируется вместе с итогом тика. Чтение сводки использует один согласованный снимок.

Восстановление. Ежедневная физическая копия с архивированием WAL вне экземпляра БД. На отдельном экземпляре проверить восстановление до выбранной точки, сверить последнюю фиксацию и пересчитать пропущенные тики по D-101–D-104. Рабочая цель испытания: RPO не более 5 минут при утрате экземпляра и RTO не более 60 минут на тестовом объёме. Граница риска после потери узла выводится из фактического отставания архива. Запись открывается только после догоняющего расчёта по D-102.

Стартовый нагрузочный сценарий — один мир, 100 виртуальных компаний, 1 000 активных ячеек, 20 запросов чтения и 5 команд в секунду в течение 10 минут. Измеряются p95 чтения до 300 мс и подтверждения приёма команды до 500 мс, обычный тик до 30 с и отсутствие частичных снимков или повторных проводок. На восстановлении выполняется тест 12 пропущенных тиков с адаптивными пакетами. Протокол измерения фиксирует CPU, RAM, версии, объём базы и задержки. Это цели для изолированного стенда, измерения ещё впереди.

Android-приёмка по D-175 и D-187 включает оба логических размера и темы, минимум два реальных устройства разных классов и проверку кадров, памяти и нагрева по [картам](maps.md). Конкретные модели и нижняя версия Android уточняются по результатам сборки и прогона.

Реальные платежи относятся к отдельному этапу. Godot передаёт серверу идентификатор покупки, сервер сверяет статус с платёжным провайдером и выдаёт право единожды на подтверждённый ID транзакции. Проверяются повтор подтверждения, отмена, возврат и окончание доступа. Провайдер, цены и даты запуска остаются отдельными решениями.
