# P3.2 — сквозная цепочка хлеба: проверка и критерии выхода

Дата: 18.11.2026. **Статус: частично реализовано; производственный профиль не утверждён.**

## Выполнено

- `scripts/check_p32_bread_journey.py` проверяет отдельную детерминированную модель сценария `docs/catalogs/wheat-bread.md` на двух вариантах поставки: вовремя и на один тик позже.
- Проверяется контрольная партия: 10 000 г подготовленного зерна, 7 400 г муки, 7 200 г муки на тесто, 24 условных буханки и 200 г остатка муки.
- Проверяются доступность доставленной муки только со следующего тика, продажа хлеба только со следующего тика после производства, отсутствие повторного списания/выручки при повторе тика, денежный баланс 2 000 → 2 340 ₽, смещение выпуска и продажи при опоздании поставки.
- Контроль не допускает скрытой смены статуса рецептов `draft_not_executable` и `reference_only`. Значения в сценарии являются **условными**, а не промышленными нормативами.

## Важное ограничение

Новый скрипт является **эталонным сценарным тестом**, а не интеграционным тестом реального Go API или Android-клиента. Ранее пройденные API/Godot smoke-тесты остаются отдельными проверками. Нельзя считать P3.2 закрытым только по этому тесту.

## Следующие действия для завершения P3.2

1. Согласовать именно **игровые** профили (не выдавая их за реальные производственные измерения) либо получить подтверждённые замеры: помол, замес, выпечка, минимальная партия, энергия, люди, качество, выход и остатки.
2. Не разблокировать DES-004 по D-139 до появления обязательных проверенных данных и версий профилей.
3. Привязать подтверждённую цепочку к реальному Go API и Android UI: склад, доставка, производство, следующий тик, продажа, деньги. Добавить интеграционный тест нескольких предприятий и перезапуска.
4. Проверить отсутствие дублирования команд, отрицательных остатков, преждевременной продажи и расхождения кассы с журналом.
5. Ручной Android-проход остаётся на P4 по ранее утверждённому порядку.

Проверка: `python3 scripts/check_p32_bread_journey.py`.

## Этапный DAG-планировщик, 18.11.2026

- Добавлен `server/game_profile_stages.go`: для изолированных игровых профилей строится граф зависимостей между линиями по товарам, далее рассчитываются топологические слои. На каждом слое все линии делят общий бюджет энергии, персонала, денег и оборудования, а при 2+ линиях применяется существующий ограниченный оптимизатор. Продукция предыдущего слоя становится входом следующего в том же тике. Одна линия участвует только в одном слое.
- `server/game_profile_stages_test.go`: две мельницы + тестомес + печь из 20 кг зерна получают 24 буханки и 7600 г остаточной муки; все 4760 Вт·ч, 4 оператора и 38000 коп. расходуются ровно один раз. Циклические зависимости блокируются без изменения снимка.
- Проверены `go test -race ./...`, `bash server/check_p32_postgres.sh`, `scripts/check_all.py`, `git diff --check`.
- **Не готово к релизу:** правила DES-002 допускают цикл с единственным запуском каждой линии по стабильному ID, а экспериментальный DAG пока намеренно блокирует циклы; не реализованы сквозные многокомпонентные группы с оптимизацией всего тика, возврат неиспользованных квот, безопасное обоснование оптимальности при 9+ линиях, межфирменные поставки и продажа продукции через новые профили. Штатный сервер/API/APK не переключены.

## DES-002: циклические зависимости (18.11.2026)

- Экспериментальный планировщик `server/game_profile_stages.go` больше не блокирует все циклы. Если в графе не осталось готовых ациклических вершин, он выбирает ещё не выполненную линию с наименьшим стабильным ID. Линия запускается максимум один раз за тик. Если стартовая линия цикла не может выполнить даже минимальную партию, весь расчёт отклоняется без изменения склада и бюджета.
- `TestGameProfileCycleRunsOnceWithSeed`: тестовый цикл `mill -> mixer -> oven -> mill` при 10 единицах стартового обратного продукта и нужных дополнительных ингредиентах выполняет ровно по одной партии на линию. При нулевом стартовом запасе обратного продукта цикл блокируется атомарно. `go test -race ./...`, изолированный PostgreSQL `check_p32_postgres.sh`, `scripts/check_all.py`, `git diff --check` пройдены.
- **Ограничение:** это безопасный локальный порядок для циклов, а не полный DES-002 оптимизатор всех взаимосвязанных линий; глобальная максимизация партий в многокомпонентном цикле, перераспределение неиспользованных квот и межфирменные резервы ещё открыты. Штатный сервер/API/APK не переключены.

**E-102, ограниченный поиск 9+ (18.11):** лимит комбинаций для больших групп снят, ограничение времени поиска 100 мс оставлено. При неполном поиске возвращается ненулевой допустимый план с `OPTIMIZER_TIME_LIMIT_UNPROVEN`; при отсутствии ненулевого допустимого плана ошибка без списания. Тест большой группы проверяет сохранение сырья и выпуск при успехе, отсутствие мутации при отказе. Это не гарантия оптимальности.

**E-103:** в `game_profile_stages.go` заменено прямое применение рассчитанных стадий на проверяемое `validateGamePlan` с безопасной арифметикой на приватных снимках. При переполнении промежуточного склада весь тик отклоняется атомарно. Тест `TestGameProfileStagesIntermediateOverflowAtomic`, Go race, vet, PostgreSQL и Python PASS.

**E-102, D-115:** при равенстве выпуска и отклонения от квот оптимизатор выбирает лексикографически больший вектор партий по возрастанию стабильных ID линий. Дробные заявки/отклонения вычисляются без предварительного целочисленного умножения. Тест `TestGameOptimizerStableIDTieBreak`, Go race и PostgreSQL PASS.

**D-116, межстадийные квоты:** `freezeGameProductionQuotas` фиксирует пропорциональные квоты по начальному складу и заявкам всех линий. В DAG новые промежуточные продукты расходуются по фактическому наличию, но вторичная цель оптимизатора использует исходные квоты. `TestGameProfileQuotasFrozenBeforeStages` PASS.

**E-102, branch-and-bound:** суффиксные верхние границы с насыщением int64 отсекают только ветви с невозможностью достичь текущего максимального выпуска. Равный выпуск не отсекается, вторичный критерий квот сохраняется. Регрессионный тест трёх конкурирующих мельниц PASS.

**E-104, модель лотов:** новый автономный `gameInventory` проверяет зрелость доставки/выпуска и резервы при отгрузке. Это тестовый изолированный слой, ещё не подключённый к реальному серверному учёту; тесты T+1 и атомарного отказа PASS.
