# EBash P2 — серверный технический срез

Тестовый контур Go и PostgreSQL по D-188–D-190. Экономика использует один сценарий хлебной цепочки и фиксированные тестовые профили. Каталог DES-004 проверяется отдельно. Подключение Godot и реальные платежи относятся к следующим этапам.

## Локальный запуск

Нужны Go 1.26 и отдельная PostgreSQL. Сборка проверена с PostgreSQL 18. Если указана база с настоящими данными, используйте отдельную тестовую БД для команд ниже.

```bash
cd server
export EBASH_DATABASE_URL='postgresql:///ebash_p2?host=/path/to/socket'
go run . migrate
export EBASH_PILOT_TOKEN="$(openssl rand -hex 24)"
go run . seed -world pilot -account pilot
go run . serve -listen 127.0.0.1:8080
```

Клиент передаёт токен как `Authorization: Bearer …`. API P2 доступен на loopback; при дальнейшем сетевом развёртывании HTTPS должен завершаться на настроенном прокси. Токены пилота выпускаются вручную; вход по email не реализован.

В другом терминале с тем же DSN рабочий процесс запускается командами `go run . tick -world pilot -tick 1` и `go run . recover -world pilot -tick 16`. Номер требуемого тика подаёт оператор теста. Восстановление блокирует новые записи до завершения догоняющего расчёта.

## Цикл через API

POST `/v1/worlds/pilot/commands` принимает следующие команды в JSON:

```json
{"command_id":"buy","type":"order_raw","payload":{"offer_id":"pilot-inputs-v1","quantity":"1","max_price_kopecks":"48000"}}
{"command_id":"line","type":"configure_line","payload":{"enterprise_id":"pilot-bakery","cell_id":"4","profile_id":"test-bread-v1"}}
{"command_id":"sale","type":"offer_output","payload":{"lot_id":"bread-3","quantity":"24","price_kopecks":"4500"}}
```

Каждая строка отправляется отдельным запросом. При покупке и настройке линии до первого тика принятое сырьё используется с тика 2, мука с тика 3, продажа с тика 4. Предложение о продаже отправляется после тика 3. Суммы указаны в копейках. GET `/v1/worlds/pilot/company` возвращает деньги, склад, ID выпущенной партии и итог продажи. GET `/v1/worlds/pilot/commands/sale` возвращает результат команды.

## Проверки

```bash
cd server
export EBASH_TEST_DATABASE_URL='postgresql:///ebash_test?host=/path/to/socket'
go test -race -count=1 -run '^TestPostgresPilot$' -v ./...
EBASH_LOAD_DURATION=10m go test -count=1 -timeout=13m -run '^TestPostgresLoad$' -v ./...
PG_BIN_DIR=/path/to/postgresql/bin bash check_restore.sh
```

Интеграционная проверка создаёт собственные тестовые миры. Проверка восстановления поднимает два временных кластера на приватных Unix-сокетах внутри `.local` и останавливает их при выходе. Копия и WAL хранятся в отдельных каталогах на том же VPS для проверки механизма. Файлы стенда остаются в `.local`.

Нагрузочный тест создаёт 100 тестовых компаний и выдаёт 20 чтений и 5 команд в секунду, тики выполняются параллельно с HTTP. Расширенный тест ведёт по десять активных ячеек на компанию. Они выполняют повторные покупки, производство и продажи через общие функции экономики и транзакционный журнал. Спрос и поставки контрольные. Эксплуатационный RPO при потере VPS и фактическая вместимость игрового мира требуют отдельных проверок.

### Результаты стенда Lunex

PostgreSQL 18.6, Go 1.26.8, 4 доступных CPU, около 7,3 ГиБ RAM. На 10-минутном прогоне получено 11 999 чтений, 2 999 команд и 599 тиков. p95 чтения составил 2,41 мс, приёма команды — 13,13 мс. Максимальная длительность тика — 69,77 мс. После уточнения состава складского снимка и стоимости остатков повторный 15-секундный прогон также прошёл. Итоговый размер тестовой базы — около 10,4 МиБ.

Проверено восстановление физической копии с WAL до тика 2 и повторное завершение 12 следующих тиков. Итог первого продающего сценария в интеграционном тесте: 24 проданные буханки, выручка 1 080 ₽, прибыль 351,35 ₽, остаток 200 г муки и 2 340 ₽ на счёте.


### Приёмочный прогон на 1 000 ячейках

На Lunex за десять минут при 100 тестовых компаниях, 20 чтениях и 5 командах в секунду выполнено 599 тиков. Журнал содержит 149 000 продаж и 1 198 000 проводок. Для каждой из 599 000 пар «ячейка и тик» записано ровно две проводки. p95 чтения — 2,11 мс, p95 приёма команды — 74,95 мс, максимальный тик — 130,35 мс.

### Восстановление вне Lunex

Опция `EBASH_RESTORE_EXPORT=1` у `check_restore.sh` сохраняет архив синтетической физической копии с WAL. Архив перенесён на отдельный облачный хост с совпадением SHA-256. PostgreSQL 18.6 восстановил тик 2, 152 000 копеек, 10 000 г зерна и две проводки. От запуска заранее подготовленного экземпляра до сверки прошло 1,069 с. Два запуска догоняющего расчёта до тика 14 заняли 129 мс суммарно и дали шесть проводок, 126 000 копеек, 200 г муки и 24 буханки. Измерения относятся к синтетической базе с заранее перенесённым архивом. Регулярная отправка WAL в постоянное внешнее хранилище ещё не настроена, эксплуатационный RPO не измерен.

### Архивирование WAL и проверенная базовая копия

Для файлового архива PostgreSQL 18 используйте уже доступный каталог на отдельном хосте. Каталог архива должен существовать только на подключённом внешнем томе: при потере подключения команда должна завершаться ошибкой, чтобы PostgreSQL повторил отправку. Файловая система должна поддерживать жёсткие ссылки и синхронизацию данных. Пути ниже подставляются из окружения развёртывания.

```ini
wal_level = replica
archive_mode = on
archive_timeout = 60s
archive_command = 'bash /path/to/server/archive_wal.sh /mnt/offsite/ebash/wal "%p" "%f"'
```

Скрипт сначала записывает и синхронизирует временный файл, затем публикует его под именем сегмента. Повтор с тем же содержимым успешен, конфликт содержимого возвращает ошибку. Каталог WAL выделяется одному кластеру.

Для ежедневной базовой копии настройте отдельное расписание с `PG_BIN_DIR` и параметрами подключения libpq. `bash base_backup.sh /mnt/offsite/ebash/base` публикует копию после проверки `pg_verifybackup`. Незавершённые каталоги скрыты и могут быть очищены после проверки, что создание копии уже завершилось.

Для контрольного прогона `PG_BIN_DIR=/path/to/postgresql/bin bash check_restore.sh` проверяет автоматическое архивирование сегмента, содержащего точку восстановления, затем восстанавливает данные и догоняет тики. `EBASH_TEST_ARCHIVE_TIMEOUT=5` ускоряет локальную диагностику. На постоянном внешнем хранилище замерять время от подтверждения тестовой транзакции до появления её сегмента именно на принимающем хосте. Порог D-190 — 5 минут. Значение `archive_timeout` само по себе не подтверждает RPO при сетевом сбое.

На изолированном стенде Lunex при интервале 60 секунд сегмент появился в архиве за 59 секунд без ручного переключения. Копия прошла проверку манифеста, восстановление вернуло тик 2 и догнало 12 тиков. Отдельно проверены повтор отправки, конфликт содержимого и недоступный каталог. Это замер локального файлового архива.

Для разового замера задержки на принимающей стороне запустите `bash check_wal_lag.sh /mnt/offsite/ebash/wal 300`. Укажите `PG_BIN_DIR` и параметры libpq для соединения с исходной PostgreSQL. Скрипт создаёт именованную точку восстановления, получает имя её сегмента и ждёт появления непустого файла. Он измеряет время от запроса к PostgreSQL до видимости сегмента и возвращает ненулевой статус при превышении порога. Используйте выделенные полномочия резервного копирования для вызова `pg_create_restore_point`. Маркер не затрагивает игровые записи. Оперативный замер дополняет восстановление из копии и WAL, которое проверяет целостность.

Локальная проверка `EBASH_TEST_WAL_PROBE=1 EBASH_TEST_ARCHIVE_TIMEOUT=5 PG_BIN_DIR=/path/to/postgresql/bin bash check_restore.sh` подтвердила видимость сегмента за 5,028 с и ожидаемый отказ на пустом архиве. Измерение при постоянном внешнем хранилище остаётся открытым.

Экспорт контрольного архива теперь записывает SHA-256 рядом с архивом. Опция `EBASH_TEST_CORRUPT_BACKUP=1` повреждает отдельную копию только внутри временного стенда и проверяет, что `pg_verifybackup` отклоняет её. Незатронутая копия используется для последующего восстановления.

### Клиентская проверка хлебного пилота из Godot

Отдельная сцена `res://Pilot.tscn` работает с тестовой цепочкой P2. Она отправляет закупку, настройку линии и продажу и отображает подтверждённые сервером деньги, зерно, муку, хлеб и статусы команд. Основная сцена прототипа открывается как прежде. Профили DES-004 допускаются к игровому исполнению отдельно по D-139.

Для автоматического прогона из `server/` задайте `PG_BIN_DIR` и `GODOT_BIN`, затем выполните `bash check_godot_pilot.sh`. Скрипт запускает локальный API и временную закрытую PostgreSQL, проводит цикл через сцену Godot и останавливает оба процесса. Тестовый токен генерируется при запуске.

Для ручного прогона на той же машине задайте в окружении Godot `EBASH_PILOT_API=http://127.0.0.1:8080`, `EBASH_PILOT_WORLD=pilot` и тот же `EBASH_PILOT_TOKEN`, с которым создан аккаунт. Запустите `godot --path prototypes/godot res://Pilot.tscn` из корня проекта. После отправки закупки и настройки линии проведите отдельным серверным процессом тики 1–3, затем обновите состояние в клиенте, выставьте хлеб и проведите тик 4. В тестовом режиме допускается только HTTP на loopback. Тики выполняет сервер, а сцена не вычисляет остатки и цену продажи.

Прогон на Lunex в Godot 4.7.2 подтвердил продажу 24 буханок, выручку 1 080 ₽, прибыль 351,35 ₽, остаток муки 200 г и баланс 2 340 ₽. Повтор тика и переоткрытие сцены дали тот же результат. Остаются визуальная проверка на Android и допуск производственного профиля.

### Играбельная демоверсия пекарни

На машине с графическим сеансом, Godot 4.7.2 и утилитами PostgreSQL задайте `GODOT_BIN` и `PG_BIN_DIR`. Из каталога `server/` запустите:

```bash
EBASH_PILOT_MODE=demo bash check_godot_pilot.sh
```

Скрипт создаёт отдельный демомир с пекарней и двумя мельницами, запускает локальный API и открывает сцену Godot. Настройте линию, выберите поставщика и нажмите «Следующий тик». Проведите две партии. Окно показывает поставки в пути, запасы, выручку и прибыль. Закрытие игры останавливает тестовые процессы. Каждый отдельный запуск создаёт новый демомир.

Для автоматического прогона используйте `EBASH_PILOT_MODE=demo-smoke`. Команда тика доступна только аккаунту `pilot` в явно включённом демомире.

### Демо производственных профилей E-104

`EBASH_PILOT_MODE=profile-demo bash check_godot_pilot.sh` открывает отдельный локальный мир пекарни с готовыми линиями замеса и выпечки. `EBASH_PILOT_MODE=profile-demo-smoke` автоматически проверяет покупку у обеих мельниц, отображение срока, склад, выпечку и продажу. Используются те же `GODOT_BIN` и `PG_BIN_DIR`. Старый режим `demo` доступен отдельно. На обычных тиках команды E-104 по-прежнему отключены.
